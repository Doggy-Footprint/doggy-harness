v2, 2026-11-17 확정. 측정 기록은 `runs.md`에 있습니다.

- v1: 스킬 본문만 보고 만들었습니다.
- v2: 기존 평가 `evaluation/brief_facts`의 채점 기준, 정답지, 측정 기록과 대조해 고쳤습니다. 받아들인 것은 각 항목에 녹였고, 받아들이지 않은 것은 아래에 이유와 함께 적었습니다.

## 기준 형상

- 대상: `harness/skills/doggy-workflow/SKILL.md`, harness 0.52.0, 커밋 2dcf9e9 (9,972단어, 375줄).
- 모든 항목의 `근거` 열은 이 본문의 줄 번호입니다. 본문이 요구하지 않는 행동은 항목이 아닙니다.
- 본문을 줄이거나 옮겨도 항목은 그대로 둡니다. 기능을 없애기로 결정했을 때만 그 기능의 항목을 지웁니다.
- 기준선에서 통과율이 낮은 항목은 "지금 본문으로도 지켜지지 않는 규칙"을 뜻하며, 그 자체가 점검 결과입니다.

## 장면

장면은 워크플로의 한 구간을 잘라 낸 것입니다. 준비한 상태에서 시작해 정해진 지점에서 멈추고, 그 사이의 기록만 채점합니다.

| 장면 | 워크플로에서의 자리 | 시작 상태 | 멈추는 지점 | 본문 범위 |
| --- | --- | --- | --- | --- |
| A 첫 메시지 | Workflow 1~2단계의 앞부분 | 저장소와 사용자 요청 | 사용자의 답을 기다리는 첫 메시지 | Decision sweep, Rounds 1, Voice, Facts, Try-n-fail search |
| B 결정에서 승인까지 | Workflow 2단계의 나머지 | A의 첫 메시지에 사용자가 답한 대화 | 승인 뒤 첫 디스패치 직전 | Rounds 2~3, Quiz, Spec 형식, Facts, Stepped specs의 권고 조건 |
| C 구현·검증 루프 | Workflow 3~7단계 | 승인된 active spec. 검증자 지적 장면은 구현·테스트가 있고 검증자 첫 보고가 도착한 상태 | 수정 지시를 다시 내보내기 직전 | Workflow 3~7, Verification model |
| D 마무리 | Workflow 8~9단계 | (D-완료) 정지 조건을 만족한 spec. (D-정지) 단계 하나가 끝난 단계 분할 spec과 "오늘은 여기까지"라는 요청 | closing report와 마무리 퀴즈 답 처리 | Closing report, Quiz의 completion questions, Stepped specs의 Ending a session |
| E 재개·중단 | Workflow 1단계 | 새 세션, active spec이 남아 있고 HEAD가 움직인 저장소 | 다음 단계의 첫 디스패치 직전, 또는 중단 완료 | Workflow 1, Stepped specs의 Resuming·Running a step·Held decisions |

### 실행 조건

같은 장면을 두 조건으로 돌릴 수 있습니다.

- **전체**: 스킬 본문 전체가 컨텍스트에 있습니다.
- **압축 뒤**: 본문의 앞 5,000토큰과 대화 요약만 있습니다. Claude Code가 자동 압축 뒤 스킬을 다시 붙이는 방식입니다. C, D 장면에 적용합니다.

## 채점 방식

| 표기 | 확인하는 곳 |
| --- | --- |
| 기록 | 격리한 telemetry 파일의 이벤트 (`HARNESS_TELEMETRY_DIR`). 훅을 거쳐 실제로 기록됐는지를 봅니다 |
| 파일 | 실행 뒤의 파일 상태: spec, `facts.md`, picks 파일, Tests diff 파일 |
| 호출 | 세션 기록의 도구 호출과 그 순서 |
| 판정 | 판정 모델이 사용자에게 보인 메시지나 서브에이전트 지시문을 읽고 판정 |
| 정답지 | 사례마다 미리 적어 둔 정답이 있어야 판정할 수 있음 |

`(금지)`는 일어나면 실패인 항목이고, `조건`은 그 상황을 만든 사례에서만 채점하는 항목입니다. 항목마다 실행 한 번에 통과, 실패, 해당 없음 중 하나를 줍니다.

## 측정 규칙

- 변형(스킬 본문의 판)은 `cfg-k` 같은 이름으로 가리고, 판정 모델은 스킬 본문을 보지 않습니다.
- 매 측정에 같은 본문의 사본 둘을 넣어 잡음 크기를 구하고, 변형 간 차이는 그보다 클 때만 읽습니다. 과거 측정에서 같은 스킬의 두 사본이 30칸 중 1~3칸 달랐습니다.
- 사례와 변형의 조합마다 5회 이상 돌립니다. 과거 측정에서 A21에 해당하는 항목이 평가자에 따라 5회 중 0~3회로 흔들렸습니다.
- 항목별 통과율은 통과 수를 해당 실행 수로 나눈 값입니다. 해당 없음은 분모에서 뺍니다.
- 판정 모델에는 채점 기준, 사례 정답지, 메시지를 이 순서로 주고, 도구 없이 정해진 JSON으로 답하게 합니다. 메시지를 하나씩 따로 판정하고, 판정마다 200자 이내의 인용을 근거로 답니다.
- 조건이 여럿인 항목(B13 등)은 조건마다 따로 기록합니다.
- 사실을 찾아내는 능력(A12~A14, A20~A22)은 첫 메시지만으로 판정합니다. 대화에서는 가상 사용자가 묻지 않은 사실을 흘릴 수 있습니다.

## 기존 실행기로 채점할 수 있는 범위

- 첫 메시지 실행기(`run_model.py`)는 읽기 도구만 주고 harness를 설치하지 않으며 도구 호출 기록을 남기지 않습니다. 메시지 내용만 보는 A06, A07, A10~A17, A19, A22는 그대로 채점할 수 있고, A20과 A21은 정답지 필드를 더하면 됩니다. A01~A05, A08, A09, A18은 채점할 수 없습니다.
- 대화 실행기(`run_dialogue.py`)는 Bash가 없고 승인 브리프에서 끝납니다. telemetry 항목(B08, B23, B27)과 승인 브리프 뒤의 항목(B24~B31)은 채점할 수 없습니다.
- 장면 C~E는 실행기와 준비 상태가 없습니다.
- 설치 실행기(`run_live.py`)는 고정한 저장소의 일회용 사본에 harness를 설치하고(원격 제거, CI 설정 생략) `/doggy-workflow <요청>`으로 실행해 도구 호출 기록과 telemetry를 남깁니다. 첫 메시지에서 끝납니다. `score_trace_a.py`가 A01~A05와 A18을 채점하고, 메시지 내용 항목은 `judge_a.py`와 `score_a.py`를 그대로 씁니다. A08, A09는 facts.md를 넣은 사례가 없어 아직 잴 수 없습니다.

## 이 표가 덮지 않는 것

- 역할별 모델 제안 (335줄).
- 변이 도구 생존자의 분류와 `equivalent` 재확인 (329줄). C23은 마커만 봅니다.
- 0.10 이전 spec의 조정 (356줄).
- 승인 브리프의 *Conflict*와 *New concept* 항목 (243~244줄). 그런 사례를 만들면 추가합니다.
- status `limit`으로 끝나는 마무리.
- 긴 실행에서만 보이는 규칙: 새 증거 없이 실패한 접근을 반복하지 않기, 수정이 진동할 때 원인 재평가 (371줄).

## 함께 적는 수치

채점 항목은 아니지만 본문을 줄인 효과를 보려고 실행마다 적습니다: 스킬을 읽는 데 든 토큰, 사용자에게 보인 메시지의 단어 수, 승인 브리프까지의 턴 수, 비용.

## 정한 것

- 실행 모델은 sonnet, effort medium입니다. 판정 모델은 sonnet입니다.
- 기준선은 기존 첫 메시지 실행기로 장면 A의 메시지 내용 항목부터 잽니다. `run_a.py`가 실행하고, `judge_a.py`가 `grader_a.md`대로 메시지를 관찰하고, `score_a.py`가 관찰에서 항목별 통과 여부를 계산합니다.
- A13은 사례의 `unknowns`를 모두 중요한 unknown으로 보고 채점합니다. 중요도 기준 표기는 아직 넣지 않았습니다.
- A20과 A21에 필요한 정답지 필드는 `case_keys.json`에 따로 둡니다.
- A01은 facts.md를 읽으려는 호출이 있으면 통과로 보고, 범위 제한 없이 읽었는지는 A01r로 따로 셉니다. A04는 telemetry에 기록된 이벤트로 채점하고, 마커 명령을 실행했는지는 A04c로 따로 셉니다. A05는 실행한 마커 명령의 인자를 판정 모델이 센 질문 수와 비교합니다.
- 본문을 옮기는 방식의 변형은 `run_live.py --config 이름=저장소+덮어쓸 폴더`로 넣습니다. `make_late_reloc.py`는 Voice, Decision sweep, Rounds를 한 글자도 바꾸지 않고 `workflow_marker.py phase --phase brief`의 출력으로 옮긴 변형을 만듭니다. 이 변형에는 phase 명령을 실행했는지(L01), 출력이 끝까지 전달됐는지(L02), 출력을 버리지 않았는지(L03)를 함께 셉니다.
