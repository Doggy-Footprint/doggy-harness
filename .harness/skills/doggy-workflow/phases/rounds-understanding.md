## Rounds

**1. Understanding round.** Before drafting, state "Here's what I understood": what the project is, where this task fits, what success looks like, and what this task will not do. Build it from every available source (project definition, README, docs, code, history, prior specs, `agent-docs/facts.md`, the conversation), not from one required file. An exclusion that drops a safeguard or cannot be added back later ("no archive before deletion", "existing rows are not migrated") is a decision: send it through the sweep instead of listing it as not done. Then list:
- *How it works today*: the touched part of the system as it stands: its parts and how they connect on the main path, where the state the task reads or writes lives, and what happens there when a step fails. Then its *inherited decisions*: choices built into that code that the task builds on or presses against (a single writer, a format others parse, a synchronous call), each with what it buys, what it costs, and when it stops holding, marked *recorded* when a spec, commit message, or doc states the reason and *inferred* when only the code shows it. A task with no existing neighbor gets one sentence on where it attaches. The user answers the questions below about code they have not read; without this model, a fact question reads as trivia and an inherited constraint stays invisible until it breaks.
- *Assumptions about the world*: each unknown behind a decision that is not significant, and each recorded fact you rely on, with its date, written as one sentence true or false whatever gets built ("assumed: one process, no concurrent writers"); the user corrects a wrong assumption faster than the decisions built on it. A sentence about what the software will do ("unsupported files are skipped") is a decision: state the fact it rests on instead ("assumed: a person watches the run and can retry a file"), and keep the decision for the approval brief. So is an existing safeguard applied to new input ("the current filters also apply to the imported data"), which decides that the safeguard is enough: state or ask what the new input contains. A decision confirmed as an assumption is approved unseen.
- *Fact questions*: each unknown behind a significant decision. Ask for the fact, not the decision: name the fact, the decision it settles, and where each answer leads. Add no guess of the answer, because a guess anchors the reply. Never move such an unknown to the assumptions to save a question: an assumption the user skims past decides a significant choice without them. There is no cap, since a fact costs the user a few words; ask nothing the repository or `agent-docs/facts.md` answers.
- *Not asked*: one line, not a list, naming each dimension on which you ask and assume nothing, with a few words on why the design is the same wherever the project stands on it ("Not asked: cost (no paid service or quota), concurrency (read-only lookup)"). Repository silence is no such reason, since silence is what makes a dimension unknown (`roadmap` and `consumers` are rarely written down); nor is edited code that does not change for that dimension, since the reason must also hold for what the change sets off (see Context pass). The user knows where this line is wrong, and it is the only place a misjudged dimension becomes visible.
- One invitation, with no examples: "If you already see decisions you want to make yourself, list them." Answering is optional. Examples would make it a hint; the decision round names candidates after the user has had the chance to see them unaided.

The round holds these parts and nothing else: no decision of this task presented as chosen or put to the user (naming the decision a fact question settles is part of that question; an inherited decision is described as it stands, not proposed), and no notes on what you searched or found missing.

Continue only after the user confirms or corrects the round. Queue a proposed `facts.md` entry for each answered fact (see Facts).
