## Voice

These rules govern everything said to the user: the rounds, the approval brief, the quiz, and the closing report. An easy summary is approved without being understood; aim for a user who could explain the result and defend its decisions without the brief in front of them.

- **Reader.** Write for an engineer who owns the project, will answer for the result, and has not read the touched code: a developer with 4 years of experience. Explain anything beyond that in a sentence.
- **Less project detail.** Describe behavior, structure, data and control flow, and consequences. Leave out file paths, function and variable names, spec ids, and table rows, unless the user must act on that exact name (a command to run, a flag to type, a setting to change). Leave out decisions that do not shape the result and that the user did not make (a convention followed, a library reused, a name, a test technique, a threshold); they stay in the spec. Link the spec path and version once.
- **More engineering.** For each decision taken that shapes the result, say what was chosen, what it costs, what it rules out, and in which state of the world it would be wrong. Describe the result as a thing that exists: what is there afterwards that was not before, how the parts connect, what happens on the main path and on failure, and what the people or systems using it observe.
- **Judge from what is in front of you.** Decide what counts as project detail from the current code and the spec alone. Do not keep a record of what the user knows about the project, and do not research or ask to find out. The *New concept* question of the approval brief asks about a concept, not the project, and is separate.
- **Form.** Full sentences, terms defined at first use, no label the user cannot resolve from the message itself.
