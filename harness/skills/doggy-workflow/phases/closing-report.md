## Closing report

End every session that worked on a spec with a closing report in chat, whether the run completed, hit the verifier limit, stopped nonterminally, or was aborted. It replaces a saved retrospective: the user reads it, and nothing in it is written to a file except the records the user approves. It follows Voice and holds, in this order:

- *What exists now*: the result as built, or the state the work stopped in; each difference from the approval brief, with the reason; and each open question left deferred.
- *Calls made during the work*: each decision taken after approval that shapes the result (an amendment, a changed approach, a dropped or added safeguard), with what it costs and rules out.
- *What went wrong*: approaches that failed and why, signals that misled, and main's own mistakes with what each cost, small ones included. This is the user's only view of a mistake that repeats across sessions.
- *Records to approve*: the exact text of each proposed `facts.md` entry, each with its own question (see Facts), and a draft of each try-n-fail record, from the execution ledger or a proposal the user rejected in conversation: an attempt whose failure took real work to discover, or a concrete rejected proposal, that a later task could plausibly try again. Write only what the user approves.
- For a stepped spec: which steps are done, what the next session starts with, and the rows this session added to `# Session Memory`, in plain words.
- *Quiz*: the closing quiz from the completion questions (see Quiz). When an answer shows that a completed result is not what the user intended, say what would have to change and ask whether to start a follow-up task; an archived spec is not reopened. While the spec is still active, handle the answer as Quiz describes. Either way, the turn that handles the reply emits the `brief` marker with `--stage quiz --quiz-of closing`, so a mismatch found at closing is counted like one found at approval.
- *Numbers*, last and in a few lines: spec path and version, completion questions marked invalid and why, verifier invocations, correction batches and their causes, mutation, fuzz, and mutation-tool outcomes, the longest Test command run's wall-clock time and, when it took longer than two minutes, its slowest single tests and the proposal to speed it up, and anything still blocked.
