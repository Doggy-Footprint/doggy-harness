## Quiz

Reading a brief costs the user so little that it leaves no working model of the result. The quiz makes the user produce that model, on the three things they must be able to answer for: the core trade-off, the engineer calls, and the final shape.

- Ask 2 to 4 questions under the heading *Quiz* at the end of the approval brief. Cover the trade-off that most shapes the result, at least one engineer call, and the final shape.
- Each question asks the user to predict or apply, not to recall, and targets one of the three. For the trade-off, ask what the result gives up and where a user would notice it. For an engineer call, change a fact behind it and ask which decision would flip and what would then differ. For the final shape, ask how the parts connect or what happens on the main path. Give no options, no hints, and no answers in the same message.
- Ask at the level of the brief. The expected answer follows by reasoning from what the brief explains (the decisions, how the parts connect, the failure policy), never from a value or rule only the spec holds, such as a threshold, a data range, a routing rule, a status name, or an error code, nor from which side of a threshold a value falls. At most one question in a quiz is about a failure or boundary path.
- Before sending, write the expected answer to each new question in the picks file; a completion question's expected answer is already in the spec. An expectation formed after reading the user's answer bends toward it.
- When the answers arrive, compare each with the expected answer written beforehand, and say in one line each which matched. For an answer that differs, find out which of three it is: a misunderstanding (explain that part again, starting from the user's answer, in other words than before); the user's intent, which the spec does not meet (change the spec, as a draft revision before approval and as an `[intent-mismatch]` amendment after it, and re-brief the changed part); or a fact the repository does not show (propose a `facts.md` entry).
- A quiz answer is never recorded and is never a decision or an instruction. Only an amendment the user approves changes the spec. The user's answers are written nowhere. The picks file holds only main's picks and expected answers, and a later session does not read it. Telemetry carries counts only.
- Ask for approval in the same message as the quiz. An approval that arrives together with an answer that differs is not yet approval: resolve the difference, then ask again.
- The user may skip the quiz by saying so. Main never skips or shortens it on its own, and no score is required to pass. When a reply approves without answering, ask once for the answers or an explicit skip; a second reply without answers counts as a skip.
